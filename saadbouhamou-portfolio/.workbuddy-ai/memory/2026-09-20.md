# 2026-09-20 — WIMA CAR case study

## Fixed the hero mockup framing (`/wima-car`)

**Reported symptom:** the `wimaAssets.home` mockup showed black/dark bars around
the screenshot in DevTools.

**Actual root cause:** `wimaScreenRatio.home` was declared as `1920 / 1040`
(1.8462) but `public/projects/wima-car/home.webp` is actually **1921×879**
(2.1854). The frame was therefore taller than the capture, so `object-contain`
letterboxed it and the frame's `bg-[#0A0A0B]` showed through as the black bands.

**Second finding:** applying only `object-cover` — as originally proposed —
would have made it worse, not better. On a frame taller than its capture,
`object-cover` fits to height and crops **horizontally**, which cut off the
WIMA CAR wordmark and the `06 61 50 34 46` CTA. `object-top` does nothing in
that case, because the overflow is horizontal.

**Third finding:** a blanket `bg-white` would have broken the other mockups.
Corner-pixel sampling showed `home.webp` is the only **light** capture
(`#ffffff`); `cover`, `fleet`, `vehicle` and `mobile` are all dark
(`#0a0a0a`–`#0b0d0f`). The backdrop has to be per-capture.

### Changes

- `src/data/wima.ts` — corrected `wimaScreenRatio` from measured dimensions
  (`cover 1586/992`, `home 1921/879`) and documented the measurement table plus
  the light/dark backdrop pairing in a comment.
- `src/app/wima-car/page.tsx`:
  - `BrowserFrame` gained a `backdrop` prop (default `bg-[#0A0A0B]`); the screen
    container is now `relative w-full overflow-hidden ${backdrop}`.
  - The hero call passes `backdrop="bg-white"`.
  - All five mockup `Image`s switched `object-contain` → `object-cover object-top`
    (`BrowserFrame`, `ScreenCard`, and the mobile phone screen).

### Verification

- `npx tsc --noEmit` and `npx eslint` both clean.
- Served HTML confirms `aspect-ratio:2.185437997724687` (= 1921/879) on the
  `overflow-hidden bg-white` container, 5× `object-cover object-top`, 0×
  `object-contain`.
- All five assets return `200 image/webp`.
- Full-page headless-Chrome capture (1440×16000, content 13217px) reviewed
  section by section: hero mockup fills the frame from the nav bar down with the
  logo and phone CTA intact; the dark `cover`, `fleet`, `vehicle` and `mobile`
  frames are unchanged and correct; `object-cover` is a no-op where the ratios
  already matched.
- Hero capture kept at `.workbuddy-ai/verification/wima-hero-after.png`.

### Screenshot recipe that works here

`agent-browser` is not installed, so use headless Chrome. The page's mount
`useEffect` scrolls back to top, so **anchor URLs are useless** — capture with a
very tall window instead and slice with Pillow:

```bash
chrome --headless=new --disable-gpu --hide-scrollbars \
  --window-size=1440,16000 --virtual-time-budget=25000 \
  --screenshot="out.png" "http://127.0.0.1:3000/wima-car"
```

`/wima-car` is ~13404px tall at 1440 wide. Note a dev server was already running
on port 3000 — check before starting another, and do not run `next build` against
the same `.next` while it is live.

### Dev-server image cache gotcha (cost most of the debugging time)

After swapping the asset, the browser kept rendering the **old dark** capture
while `curl` returned the new light one. Cause: the Turbopack dev server caches
optimized images at `.next/dev/cache/images/`, keyed by
(url, width, quality, **negotiated format**). Chrome sends
`Accept: image/avif,image/webp,...` and curl sends `*/*`, so the two got
different cache entries — the Chrome-flavoured one held pre-swap bytes.

Reproduce the split with:

```bash
curl -s -H "Accept: image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8" \
  "http://localhost:3000/_next/image?url=%2Fprojects%2Fwima-car%2Ffleet.webp&w=500&q=90" -o x.bin
```

Diagnosis rule: **if the page renders a stale image but `curl` on the same
optimizer URL returns the new one, add Chrome's `Accept` header to the curl.**
Deleting the cache file does not help — the dev server keeps it in memory, so
the only real fix is restarting `next dev`. A fresh `--user-data-dir` does not
help either; the staleness is server-side.

Also: `.next/dev/cache/images` is a cache and safe to clear, but the safe-delete
shim refuses it unless `CODEBUDDY_SAFE_DELETE_ENABLED=0` is set.

- `tsc --noEmit` and `eslint` clean.
- Served HTML: `aspect-ratio:0.6401384083044983`, one `bg-white` and one
  `bg-[#0A0A0B]` ScreenCard container.
- Rendered and confirmed the fleet tile now shows the light catalog capture
  filling the frame with no bands (captured at a 2000px viewport, because at

  cache).
- Evidence: `.workbuddy-ai/verification/gallery-after.png`.

### Side effect, and the fix chosen

The new capture is portrait (0.640) where the others are landscape (vehicle
1.385, mobile 0.474). In the 3-column gallery the grid row stretches to the
tallest card and `ScreenCard`'s screen box is `flex-1`, so the vehicle tile's
container grew past its own ratio and `object-cover` cropped the vehicle
screenshot hard (the "RENAULT CLIO 5" heading, the price and the RÉSERVER button
were all cut off).

User chose `object-contain` for the tiles. Applied to `ScreenCard` and the
mobile phone screen. Because each tile's backdrop now matches its capture's own
page background, the resulting letterbox is **invisible** — nothing is cropped
and the text blocks stay aligned across the row. This is the same pattern the
mono page uses (`backdrop = "bg-[#F8F8F8]"`).

So the page now has two deliberate rules:

| Where | Class | Why |
|---|---|---|
| `ScreenCard`, phone screen | `object-contain` | Row stretch makes containers mismatch their capture ratio — contain letterboxes invisibly instead of cropping |
| `BrowserFrame` (hero, cover) | `object-cover object-top` | Standalone frames whose ratio matches the capture exactly, so it is a no-op; kept as originally requested |

Re-verified after the change: vehicle tile shows its full capture again, fleet
tile still fills its frame, hero unchanged. Evidence:
`.workbuddy-ai/verification/gallery-after.png` and `hero-after.png`.

## Fixed the sticky in-page section nav (`/wima-car`)

**Reported symptom:** the `01 Challenge … 11 Next` bar "leaks out or clips
awkwardly to the far left, lacks proper alignment, and feels unpolished."

**Actual root cause — the bar was never sticking at all.** `src/app/globals.css`
set `overflow-x: hidden` on **both `html` and `body`**. Setting `hidden` on one
axis forces the other to compute to `auto`, so `<body>` became a scroll
container. A `position: sticky` descendant is confined to the nearest
scrollport — `<body>`'s — and since `<body>` only grows to fit its content it
never scrolls internally, so the bar just scrolled away with the page.

Chain that mattered (before the fix):

| Element | overflow-x | overflow-y | scroll container? |
|---|---|---|---|
| nav's parent div | visible | visible | no — `position: sticky`, but trapped |
| `main` | `hidden` → **`clip`** | `auto` → `visible` | yes → no |
| `body` | `hidden` | `auto` | **yes — this was the trap** |
| `html` | `hidden` | `auto` | yes |

**The rule:** `position: sticky` cannot escape an ancestor whose overflow is
anything other than `visible` or `clip`. `overflow-x: hidden` on `html`/`body`
is the classic way to break sticky site-wide.

### Changes

- `src/app/globals.css` — `html, body` now use `overflow-x: clip` instead of
  `overflow-x: hidden`, preserving the "kill horizontal scroll on mobile"
  intent (verified: `documentElement.scrollWidth - clientWidth === 0`) without
  creating a scroll container. Added an `@supports not (overflow: clip)`
  fallback that puts `hidden` on `html` only — which still trims the viewport's
  horizontal overflow but does not turn `body` into a scroll container.
- `src/app/wima-car/page.tsx` — `<main>` changed from `overflow-x-hidden` to
  `overflow-x-clip` for the same reason.
- Section nav rewritten:
  - Wrapped in `<Container className="relative">` so it is centred on
    `max-w-7xl` and its first pill lines up exactly with the page content grid
    (measured: first pill left = 112px = 80px container inset + 32px gutter).
  - Strip keeps `-mx-4/6/8 px-4/6/8 scroll-px-4/6/8` so items bleed to the
    container edge while `scroll-padding-inline` preserves the gutter when the
    browser scrolls an item into view.
  - Bar is `sticky top-[58px] z-40 … sm:top-[72px]`, `bg-[#0A0A0B]/80
    backdrop-blur-md border-y border-white/10`.
  - Added directional edge fades (`navEdges` state, rAF-throttled measurement of
    `scrollWidth - clientWidth` vs `scrollLeft`) because the strip hides its
    scrollbar. A 400ms delayed re-measure catches webfonts landing after first
    paint.
  - Active pill: `border-[#D71920] bg-[#D71920]/10 text-white` plus a red glow
    `shadow-[0_0_18px_-6px_rgba(215,25,32,0.75)]`; hover adds
    `hover:bg-[#D71920]/10` on top of the existing `hover:border-[#D71920]/50`.

### Verification (measured, not eyeballed)

A CDP harness (raw WebSocket, Node 22 global `WebSocket`, no npm install)
reported, after the fix:

- Desktop 1440×900 — `barViewportTop` 1611 at rest → **72** at scrollY 3200 and
  7400, i.e. pinned exactly at its `top-[72px]` offset.
- Mobile 390×844 — pinned at **58**; strip content 1082px in a 390px client, so

- `tsc --noEmit` and `eslint` clean.

### Gotcha: React does not hydrate in this sandbox's headless Chrome

The active-pill and edge-fade *state transitions* could not be observed live:
`window.__spyMount` was null and `data-active` never appeared. Diagnosed by
probing `document.documentElement.classList.contains('lenis')` (false) and
counting nodes carrying `__react*` own properties (2 of 1201). **The home page
`/` behaves identically**, so this is environmental, not a page bug — the
sandbox blocks the `/_next/webpack-hmr` websocket
(`ERR_INVALID_HTTP_RESPONSE`) and hydration never completes on any route.

Workaround used to verify the *design* anyway: temporarily seed the initial
state (`useState<string>("#wima-platform")`,
`useState({ start: false, end: true })`) so the active pill and the right-hand
fade render through SSR, screenshot, then revert. This proved the red border
(`rgb(215,25,32)`), the `bg-[#D71920]/10` tint, the glow, the fade gradient and
the `data-active="true"` attribute all render correctly. Evidence:
`.workbuddy-ai/verification/nav-band-desktop.png`, `nav-band-mobile.png`.

Note also that without hydration `Navbar`'s `isScrolled` stays false, so
headless captures always show the navbar in its un-scrolled state (`top-0`,
`py-4`), never the rounded pill at `top-2 sm:top-4`. Clearance still checks out:
navbar bottom ≈54px (mobile) / ≈62px (desktop) vs bar tops 58px / 72px.
